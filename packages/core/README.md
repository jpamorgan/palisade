# @palisade/core

Runtime-neutral audit catalog, validation, deterministic scoring and bounded provider adapters. All mutations return a new workspace. They never change device or account settings.

The catalog contains 38 controls in eight weighted areas. Every control has explicit verification, freshness and remediation instructions. Checks with a documented partial condition earn exactly half their points. Other controls accept pass, fail, unknown or explained non-applicability.

Scoring uses reduced rational arithmetic and half-up rounding. Within each area, applicable controls share the area's points by catalog weight. Non-applicable controls redistribute points inside their area; entirely non-applicable areas leave the denominator. Each repeated control uses the weakest result across all explicitly added matching assets, and every applicable scoped subject must have fresh accepted evidence before the aggregate earns or assesses points. The critical flag affects recovery review priorities, never inclusion in the score. Missing asset inventory remains unknown. Adding healthy assets cannot dilute an existing failure. `CheckResult.subjects` explains every contributing observation.

Unknown, stale, imported, unsupported and same-time conflicting observations earn no verified points and no coverage. A resolved failure earns coverage, but no posture points. At zero coverage the score is `null` (not assessed). Newer observations supersede earlier observations; equal observation instants with differing statuses require a new verification. Evidence exactly at its freshness boundary remains fresh. Guided verification can earn full credit and must describe the actual procedure and result; action completion creates no evidence. Findings keep known serious gaps visible even when another subject in the same control is unresolved.

`WorkspaceSchema.parse` validates trusted local persistence. `validateImport` validates untrusted JSON and downgrades all observations to historical imported evidence, removes imported score snapshots and resets event relevance. `mergeWorkspace` remaps incoming asset identifiers, deduplicates imported observations, preserves trusted evidence, imports completion records as plans and never accepts an imported score. Existing workspace settings are retained. Import timestamps are historical; fresh verification is required. Snapshots preserve evaluation, scope identifiers, settings and rules versions. The v1 limits are 200 assets, 10,000 observations, 5,000 actions, 100 snapshots and 2,000 threat records; exceeding a limit produces an explicit export/new-workspace error rather than silently deleting history.

Hosted callers must derive `method` themselves: user/MCP submissions are guided or imported, while authorized collector/provider paths set their own provenance. The core API is a library, not an authentication boundary. Evidence notes and facts reject recognizable credential formats and sensitive field names, but callers must still avoid submitting secrets in free text. Identity assets accept labels only, never document numbers.

`updateAsset(workspace, id, patch, now?)` edits label, identifier value, critical status or recovery dependencies while retaining the asset ID and history. An empty value clears the optional identifier; an omitted value is unchanged. Label-only and critical-only edits preserve evidence and score. Changing an identifier appends unknown observations for existing checks on that asset and recovery checks on transitively dependent accounts. Changing recovery routes, or removing a recovery asset, reopens affected recovery checks. Equivalent email case and recovery-edge ordering do not trigger invalidation. New unknown invalidations take precedence over observations at the same instant; a later fresh check resolves them. Original observations and snapshots remain intact. Pending HIBP and public-search results are bound to their queried identifier and rejected if that identifier changed before application.

HIBP exact-address lookups require a valid subscription key, explicit consent to disclose the address and verified ownership. They never silently fall back from a privacy-preserving lookup. HIBP's public API coverage excludes sensitive and retired breaches; a 404 is a scoped no-match. A successful lookup passes only the breach-review control; historical breach events remain even after remediation. Public CISA KEV and HIBP catalog reports always enter with unassessed personal relevance. Brave public search requires a configured key and explicit query disclosure consent, and returns unconfirmed matches without assigning a prominence score. Adapters use fixed endpoints, prohibit credential-bearing redirects, cap response bytes and enforce timeouts over the entire streamed response.

Provider references: [HIBP API](https://haveibeenpwned.com/API/v3), [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog), [Brave Search API](https://api-dashboard.search.brave.com/app/documentation/web-search/get-started).
